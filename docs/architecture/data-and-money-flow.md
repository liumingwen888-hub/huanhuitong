# 数据与资金流

需求状态：APPROVED。交付状态：DESIGNING。

## 身份入口

Telegram Webhook 经 HTTPS 与 secret token 验证、Update 去重、大小与类型校验后进入适配器。适配器提取稳定 user.id，调用身份用例解析或在一个身份事务中幂等创建 UID、会员关系、Telegram 绑定、最小资料和注册记录；username 只作为可更新展示属性。身份事务不创建具体资产账本账户、链上地址、钱包、充提网络或换汇市场。业务响应与通知写入 Outbox，避免外部消息与数据库事务形成双写。

阶段 1 v1.2 计划要求 Inbox 对最小化、规范化 Update 生成稳定 digest：同 `update_id` 同 digest 返回 duplicate_same_payload；同 ID 异 digest 进入 conflict，不覆盖原记录且不产生业务效果。RECEIVED→CLAIMED→PROCESSED 与身份和 Outbox 在同一 UoW 内完成，崩溃/超时只允许新 claim generation 重领。注册幂等键由服务端从可信 Telegram 主体和 `start` 事件确定派生，公共命令不接收任意 registrationKey。

## 资产账户开通

UidCreated 只声明身份已建立，不产生资金变化，也不要求所有资产账户存在。资产目录批准并启用后，由应用编排显式调用账本 EnsureAssetAccount，或在用户首次使用该资产时懒创建；最终策略在资产与账本实施设计中确定。接口按 UID、资产和用途幂等，重复事件或重试不能创建重复账户。主菜单和余额查询只展示已批准、已启用的能力；交易对目录不能触发账户、地址或市场创建。

## 内部转账与领取

内部转账在单个数据库事务中验证命令幂等键、付款授权、风险、费用和可用余额，创建订单与账本交易，从付款方可用账户转至收款方可用账户并分离费用。领取模式先从付款方可用转入平台领取负债/冻结账户；收款人成功领取后转入其可用账户，到期或撤回则冲回付款方。领取令牌只保存安全摘要，成功消费使用条件更新或唯一约束保证一次性。

## 充值

Scanner 以链、网络、交易哈希、输出索引等稳定键写入链上观察 Inbox；确认策略把观察推进到可入账，账本从外部托管资产对应账户记入用户可用或在途账户。重组通过状态机和补偿分录处理，不能删除已过账历史。归集是独立链上任务，不重复用户入账。

## 提现

提现请求先预留用户资金，审批后生成不含私钥的签名意图。Signer 返回签名结果，Broadcaster 广播，Confirmation Worker 查询链上结果。广播 UNKNOWN 时资金继续冻结且禁止新交易替代；确定失败释放，确定成功结算用户负债、链上托管资产、费用和成本。

## 换汇与法币代付

换汇报价保存来源、时间、有效期、精度、费用和舍入快照；确认后预留卖出资产，执行结果确定后用成对资产账户结算，失败释放，未知保持冻结并查询。法币代付同样预留后提交供应商；回调仅作经验证的状态输入，主动查询与对账共同决定最终状态，UNKNOWN 不触发重付。

## 查询与审计

余额是账本投影，可重建；账单关联业务订单和账本交易；审计记录操作者、授权、前后状态摘要和原因，不保存密码、令牌、密钥或完整敏感数据。

## 阶段 1 实施事实（2026-08-17）

身份数据流已实施并经真实验收：Telegram Update → Webhook 五道门禁 → Inbox 认领（完整 parsed Update HMAC）→ ResolveOrCreateUid（幂等竞争 + 唯一绑定双防线）→ 身份事件与主菜单事件同事务入 Outbox → worker at-least-once 投递。资金流（充值/提现/换汇/代付）未开始，属阶段 3+。
